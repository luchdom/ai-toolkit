# Choosing a .NET test boundary

Start with the target repository's architecture docs, test projects, and validation commands. The repository owns its rules and test layout. Choose a boundary where the failure you care about would be visible.

- For a business rule, exercise the application code and substitute its external dependencies when isolation helps. For an HTTP contract, send a request through the app's test host and check the caller-visible result. An HTTP test can verify both a functional requirement and the interaction between routing, binding, and application code. [Microsoft's functional testing guide](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/test-asp-net-core-mvc-apps#functional-tests) and [ASP.NET Core integration tests](https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests).
- For SQL translation, migrations, constraints, or transactions, use an isolated instance of the production database engine. A repository stub can exercise a caller's response to a database failure. Record which provider or substitute ran. [EF Core testing strategy](https://learn.microsoft.com/en-us/ef/core/testing/choosing-a-testing-strategy).
- For a structural convention, start with the repo's documented rule and existing analyzer or architecture suite. A representative violating example should fail its check. Follow the repository's decision about grouping tests in folders or projects. [Microsoft's guidance on organizing test projects](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/test-asp-net-core-mvc-apps#organizing-test-projects).
